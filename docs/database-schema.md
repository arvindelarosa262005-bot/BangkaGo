# Database and invariants

All identifiers use UUIDs; booking references are random unique human-readable `BG-…` values. All money columns ending `_minor` are **integer centavos**, currency PHP. Commission rates use integer basis points (1000 = 10%); PostgreSQL numeric rounding is half up for positive values. The client helper uses BigInt division with the same policy. No binary floating-point arithmetic is used for stored financial calculations.

| Domain                 | Tables                                                                                     |
| ---------------------- | ------------------------------------------------------------------------------------------ |
| Identity               | profiles, boat_owners                                                                      |
| Geography and listings | locations, routes, boats, boat_images                                                      |
| Verification           | document_requirements, boat_documents                                                      |
| Reservations           | boat_schedules, bookings                                                                   |
| Money                  | commission_rules, payments, payment_webhook_events, platform_commissions, refunds, payouts |
| Experience             | reviews, notifications, support_tickets, saved_boats                                       |
| Governance             | admin_audit_logs, app_settings                                                             |

An owner profile may own multiple boats. Each schedule belongs to one boat and route, with seat or charter mode and its own price/capacity. A charter reserves the entire capacity irrespective of passenger count. A seat booking reserves its passenger count. Both models cannot share a schedule. Arrival and departure are timestamptz; display and form interpretation use Asia/Manila (UTC+08). No naive date value is stored as a trip timestamp.

`pending_owner_confirmation → awaiting_payment → confirmed → completed` is the successful path. Pending/awaiting bookings can cancel or expire; pending requests can reject. A confirmed predeparture cancellation moves to refund_pending. Late verified payments also move cancelled/expired bookings to refund_pending. Only provider-confirmed refunds move to refunded. Terminal states cannot be reopened by clients. Refunds are full-amount in this initial policy; partial-refund policy requires an additional reviewed allocation model.

Boat registration: draft → submitted → under_review → approved / needs_correction / rejected. Corrections reopen a draft and require reapproval. Administrators can suspend. Expired documents immediately remove public booking eligibility even when stored boat status still reads approved. Owners cannot change verification, ownership or payout fields. Registration edits require no active future schedules; currently close schedules still count until their end to protect earlier bookings.

`schema.sql` and `operations.sql` are authoring sources. The migration generated by Supabase CLI concatenates them; update the migration before its initial deployment only. Once applied to any persistent project, add a new migration rather than rewriting history.

Do not delete auth users without a retention/account closure plan: foreign keys intentionally protect financial and audit records. Personal contact fields remain in private profiles; the public availability RPC publishes only operator display name and approved boat information.
